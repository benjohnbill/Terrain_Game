Game Stack Literacy · Lesson 2

Applying the model: the L3 build decisions

Six choices just got made in gate 05. Sort each one into the four layers you already know — and meet the one axis the model doesn’t show.

In Lesson 1 you learned the four-layer model, and noticed something: at three of the four layers, this game ran on nothing — no framework, no build tool, no packaging beyond a URL. Those empty layers were a deliberate starting point, waiting to be filled when a real need appeared.

The L3 build is that need. gate 05 is the first decision batch that actually fills the empty layers. We just made six choices in it (I called them D1–D6 while we talked). Six decisions in unfamiliar vocabulary feels like a lot. This lesson does one thing: it drops each of the six into a layer you already know, and shows that almost all of them are the cheap, reversible kind — with exactly two carrying real new weight.

Read the “Now” lines: gate 05 is almost entirely a Layer-2 and Layer-3 event. The only Layer-1 move is adding TypeScript, and even that is not the expensive kind. TypeScript is JavaScript with type labels; a compiler strips the labels and emits plain JavaScript, which is what actually runs. You never leave the JS runtime. (That “strip the labels and emit JS” step is transpiling, and it’s the single fact under half our decisions.)

Key insight Of the six gate-05 decisions, only two carry real new weight: adding TypeScript at Layer 1 (and even that never leaves JavaScript), and D5, where the documentation governance has to follow the code as it moves house. The other four are cheap, reversible Layer-2/3 plumbing — naming folders, naming commands, picking test runners.

▸ “D4” isn’t missing — it folded into D3. Choosing the test runners (node:test for logic, Playwright for the browser) is part of naming the command surface.

Notice the shape. D1, D2, D3, D6 are all pure build plumbing — where files sit, what commands are called, how logic is compiled. None of them touch the meaning of a single game term. Only D5 reaches into the other world you already know — and that’s the part worth its own section.

The fifth axis the model doesn’t draw: governance

The four-layer model answers one question: how does code get built and reach a player? But this repository runs a second axis, at a right angle to the first, that the stack model never shows — documentation governance. It answers a different question: do the documents, the terms, and the code still agree with each other?

You already know its machinery, because you built it:

  • docs/audits/term-inventory.json — the machine-readable index of every sealed term. Each term can claim a code identifier and the files it lives in (codeRefs).
  • scripts/audit-lint.js — among its checks, the code-contract one: “does the identifier this term claims to have actually exist in the files it points at?” If not, the doc and the code have drifted.
  • scripts/hooks/write-lint.js — the hook that runs that audit automatically after you edit a governed file, and shows the findings (it never blocks the edit).
  • docs/SYNC-DEBT.md — the ledger where any unpaid drift is recorded on purpose.

▸ This is why “I couldn’t connect the stack decisions to the doc-audit/hook world” was the correct feeling. They mostly don’t connect. Four of five decisions live purely on the build axis and never touch governance at all.

Here is the point that unlocks the whole thing: most stack decisions never meet the governance axis. D1, D2, D3, D6 are invisible to term-inventory and audit-lint — moving a folder or naming a command changes no term’s meaning. The two axes are independent.

They cross at exactly one point, and that point is D5. Here’s the chain, slowly:

Why D5 is the crossing Today, 27 sealed terms carry a code pointer that says “my implementation is in js/….”  →  ADR 0041 just declared js/ a reference archive; the real code is being re-implemented under game/.  →  So when a term’s behavior moves house to game/, its code pointer must move with it, and audit-lint (which only ever looked inside js/) must be taught to look in the new tree too.  That re-aiming is D5. It is the only place a build decision and a documentation contract touch.

So the mental picture to leave with: a horizontal build stack (four layers) and a vertical governance axis. gate 05’s six decisions are almost all on the build stack; a single wire (D5) runs across to the governance axis, and only because the code is changing address.

Check yourself

Same four layers as Lesson 1, plus one option for the governance axis. Pick where each decision lives. Guess, then read the feedback — retrieval is the point.

“Replace the hand-written js/ui.js with React components.”

React changes how UI code is structured inside the runtime, Layer 2. It fills an empty layer and replaces the UI only; the logic modules are untouched.

“Add Vite and Playwright so I have a dev server and a browser test.”

Both turn source into runnable/shippable artifacts at Layer 3. Additive and low-cost; your JavaScript and its logic are unchanged.

“Adopt TypeScript for all new code.” Is this a Godot-style Layer-1 rewrite?”

TypeScript sits at Layer 1 but compiles down to JavaScript, which is what runs. You never leave the JS runtime — so it is nothing like a Godot/GDScript rewrite. This is the one “new weight” move that is still cheap because it never leaves the language family.

“audit-lint will break when a term’s code moves from js/ to game/.” Which axis is this?”

This is the governance axis, the term↔code contract, not the build stack. It is the single point (D5) where a build decision (moving code to game/) crosses into documentation governance. Every other gate-05 decision stays on the build stack.

Primary source

The three documents this lesson is built on, worth reading with the model in hand:

  • ADR 0041 — why js/ becomes a reference archive and L3 gets its own tree. This is the decision that makes D5 necessary.
  • ADR 0040 — why canonical L3 source is TypeScript/ESM. This is the Layer-1 “new weight” in the key insight.
  • gate 05 ticket — the option space for D1–D3 and D6, in the project’s own words.

This lesson is your mission in action: taking a real, scary-looking stack decision and defending it by sorting it into layers — seeing that most of it is cheap, and naming precisely the parts that aren’t.
