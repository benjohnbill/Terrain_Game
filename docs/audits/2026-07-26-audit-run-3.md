## The status values, and the ruling that already covers them

The `status` field carries `SEALED` ×10, `AGREED-concept` ×2,
`AGREED-structure` ×1, `가안` ×1, `SUPERSEDED` ×1 — all off the Vocabulary Law's
three-word dictionary (`AGREED/PROPOSED/rejected-recorded`), while the Conflict
rule separately names a *different* three (`SEALED/AGREED/CONFIRMED`). Every one
of these values is **faithful to its source document**: the inventory is indexing
correctly and the divergence is in the law.

This run left them untouched and reported the divergence as a user question.
**Ticket 03 § Q1 had already answered it** (2026-07-15): extend the dictionary,
because the law contradicts itself and `SEALED` marks a real distinction —
9 of the 10 `SEALED` rows come from a single birthplace, which is authored intent
rather than typos, and the ruling notes the same enum drifted again within 5 days
when only prose forbade it. Leaving the values alone was the right *action*;
calling it an open question was wrong. Applying the ruling (law line + `HARVEST.md`
§4, batched, Tier-3) is what remains.

One caution the ruling itself raises and this run confirms: extending the
dictionary buys precision for *future* rows only. It says nothing about how many
of the 235 existing `AGREED` rows actually carry a seal — and
`MARKER_OK['✅'] = (s) => s !== 'PROPOSED'` means a `SEALED` row already passed
`checkStatusMarkers` before the ruling existed. The enum fix is a naming fix, not
a verification mechanism.
